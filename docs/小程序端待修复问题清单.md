## 一、买家商城端（wms-shopping-miniapp）

### MALL-P0-1 「直接购买」下单的是整辆购物车 【P0】

- **位置**：`src/pages/product/product.vue:109-121`（doBuy 弹窗）、`product.vue:121-123`（goCheckout）、`src/pages/checkout/checkout.vue:115-129`（submit）
- **问题**：商品页弹窗确认「购买『该商品』× 1（¥xx）」，确认后 `goCheckout()` 仅 `uni.navigateTo('/pages/checkout/checkout')`——既未把该商品加购，也未传商品参数；结算页 `submit()` 永远按整辆购物车调 `orders.create`（后端 `MarketService.createOrder` 遍历全部购物车行）。
- **影响**：用户确认买 A，实际生成的订单可能包含完全不同的商品、数量与金额。属于订单一致性事故。
- **修复建议**：方案 A——doBuy 先 `cartApi.add(productId, 1)` 成功后再跳结算页（注意提示用户购物车将包含其它已加购商品）；方案 B——支持 buyNow 链路：下单接口增加 `buyNowProductId/quantity` 参数，后端跳过购物车按指定商品下单。无论哪种方案，结算页都需展示将下单的商品明细。

### MALL-P0-2 payType 后端不校验权限，挂账审核即自动收款 【P0，含后端】

- **位置**：
  - 前端：`src/pages/checkout/checkout.vue:79-85`（挂账 CREDIT 入口仅 `user.role === 'ADMIN'` 可见，注释 P2-10）
  - 后端：`wms-server/.../controller/market/MarketController.java:180-183`（`POST /market/orders` 仅 `SecurityUtils.require(MARKET_BUY)`）、`service/market/MarketService.java:305`（`MarketPayType.from(req.payType())` 无任何角色校验）
  - 关键放大器：`MarketService.java:546-555`——`audit()` 通过时**非在线支付订单自动扣库存 + 置 `AUDITED` + `payStatus=PAID` + 写 `paidAt`**（该规则本意是货到付款收款凭线下，但 CREDIT 同样命中）；`ship()`（:573）只要求 `PAID` 即可发货。
- **影响**：任意 CUSTOMER 直接构造请求传 `payType=CREDIT` 或 `CASH_ON_DELIVERY` 即可绕过前端限制下单；管理员审核通过后订单自动记为已收款、库存扣减、可发货——顾客自助完成「零支付拿货」链路。前端 P2-10 的安全假设（入口仅管理员可见）在 API 层完全不成立。
- **修复建议**：
  1. `createOrder` 服务端校验 payType：`CREDIT` 仅允许具备特定权限（如新增 `market:credit`，仅 ADMIN/FINANCE）的账号使用；`CASH_ON_DELIVERY` 视业务决定是否放开给 CUSTOMER。
  2. `audit()` 自动置 PAID 的分支改为按 payType 白名单（至少把 CREDIT 排除，改为单独的财务确认动作），或在 UI/日志上向审核员强提示"该订单顾客自助选择了挂账"。

### MALL-P1-1 结算页展示金额与下单金额口径不一致 【P1，含后端】

- **位置**：购物车/结算合计来自 `/market/cart`，按原始快照价计算（`MarketController.java:115`、`:343`）；下单金额走 `MarketService.effectivePrice()`（快照超 7 天或无效回退现价，`MarketService.java:312-317`）；前端直接展示 `store.total`（`checkout.vue:56-62`）。
- **影响**：管理员调价后，快照过期的购物车在结算页显示的「应付」与生成的 `totalAmount` 不同，无任何提示。易产生客诉。
- **修复建议**：结算页改为请求后端按 effectivePrice 口径重算（新增接口或 `/market/cart` 支持 `pricing=effective` 参数）；退而求其次，在结算页固定展示"商品价格以下单实价为准"。

### MALL-P1-2 支付成功后无查单/轮询 【P1】

- **位置**：`src/utils/pay.js`、`src/pages/order-detail/order-detail.vue:107-112`、`src/pages/orders/orders.vue:77-82`
- **问题**：`uni.requestPayment` success 后只 toast + 单次 `load()`。真实模式下前端 success ≠ 后端回调已落单；回调延迟时页面停留 PENDING/UNPAID，「立即支付」仍在，用户可重复拉起收银台。全工程无任何轮询（grep 证实）。
- **修复建议**：success 后进入轮询：每 1.5~2s 查 `orders.detail(id)`，确认 `payStatus === 'PAID'` 再刷新 UI，次数上限（如 10 次）后降级为"支付结果确认中，请稍后刷新"。失败/取消分支维持现状。

### MALL-P2-1 「我的」页订单计数被分页钳制 【P2】

- **位置**：`src/pages/mine/mine.vue:79`（`orderApi.list({ pageSize: 100 })` 后前端按状态过滤计数）；后端 `MarketController.java:194` 钳制 `Math.min(50, pageSize)`。
- **影响**：订单超过 50 条后各状态角标系统性偏小，可能让用户看不到待付款订单。
- **修复建议**：后端提供按状态分组的 count 接口；短期可让前端按状态分别带 `status` 参数请求 `pageSize=1` 取 `total`。

### MALL-P2-2 cart store 加载失败不重置且异常上抛 【P2】

- **位置**：`src/store/cart.js:11-21`（try/finally 无 catch）；调用方 `pages/cart/cart.vue:44`、`pages/checkout/checkout.vue:87-89` 均无容错。
- **影响**：网络失败 = unhandled rejection、页面无提示；失败时 `items/total/count` 保留上一次成功值（pinia 跨页单例，可能是上一账号的脏数据）；checkout 中 cart.load 失败还会中断后续 `loadAddresses/loadWarehouses`，页面静默残缺。
- **修复建议**：`load()` 失败时重置为空态并向上抛出可展示的错误；checkout 侧将三个加载改为并行且各自 try/catch。

### MALL-P2-3 下单成功后 clear() 失败被误报「下单失败」 【P2】

- **位置**：`src/pages/checkout/checkout.vue:127-131`；后端 `MarketService.java:338` 下单时已 `carts.deleteByUserId` 清空购物车。
- **影响**：`orders.create` 成功后前端 `useCartStore().clear()` 若网络抖动抛错，进入 catch toast 错误——订单其实已创建；用户重试只会得到「购物车为空」（`MarketService.java:296`）。
- **修复建议**：下单成功即认为流程完成，clear() 移出 try（或 catch 吞掉），同时本地直接置空 store 状态替代远程调用。

### MALL-P2-4 「确认收货」无二次确认 【P2】

### WMS-P1-4 冷启动永远落在登录页；401 无防重、丢现场 【P1】

## 三、两端共有基建问题

### COMMON-P1-1 幂等 pending 存储只增不减 【P1】

- **位置**：`wms-miniapp/src/api/request.js:39-44`、`wms-shopping-miniapp/src/api/request.js:28-33`——`clearRequestIdentity` 仅在成功路径调用；401、4xx/5xx、网络 fail、业务码非 200 均不清 key。
- **影响**：失败的提交永久留在 `wms_idempotency_pending`，storage 只增不减；失败后重试同一表单永远复用同一 key（服务端幂等按 `(username, scope, key)` 唯一且无响应缓存时无害，但依赖该语义）。
- **修复建议**：业务终态（成功或后端明确拒绝）即清 key；网络 fail 保留 key 以支持重试；同时给该 map 加条目上限/TTL 清理。每次写请求同步读写 storage 两次可合并为一次内存缓存 + 惰性落盘。

### COMMON-P2-1 401 → reLaunch 无并发防重 【P2】

- **位置**：两端 `request.js` 401 分支。
- **说明**：token 过期时页面并发多请求会同时收到一串 401，各自触发 `clearToken` + `reLaunch`。wms-web `src/api/client.js` 已有按 Authorization 批次去重的约定（AGENTS.md 明示），两个小程序应对齐。
- **修复建议**：记录首次 401 请求的 token，同批次只执行一次清理+跳转。
