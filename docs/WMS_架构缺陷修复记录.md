# WMS 架构缺陷审计与修复记录

审计范围：Spring Boot 服务、JPA Repository、Vue 与两个微信小程序的 API 调用路径。结论来自静态源码检查；尚未进行 MySQL 并发压测或安全渗透验证。

## 审计摘要

审计识别出 8 项高风险、6 项中风险。现有库存行使用数据库悲观锁，普通出库有库存边界检查；主要风险来自库存键空值、预占与物理库存口径不统一、并发快照，以及重复请求和状态流程。当前没有波次/拣货单实现。商城支付回调已有订单锁和已支付幂等检查。

## 逐项修复记录

修复状态只在对应代码改动完成后更新。验证项记录静态检查、构建或测试结果；未执行的验证会明确标注。

### 1. 买家越权读取后台客户列表

- 状态：已修复
- 修复内容：增加 `customer:read-all` 权限，仅授予后台业务角色；商城 `CUSTOMER` 角色只保留商城读写权限；后台全量客户列表改为检查新权限。
- 验证：静态检查角色矩阵与接口权限调用点；后端编译与默认 profile 启动通过；未运行测试。

### 2. 仓库级数据授权

- 状态：已修复
- 修复内容：新增 `user_warehouse_access` 关系表、仓库访问服务和用户管理页多选配置。仓储角色无绑定时拒绝访问；库存出入库、调拨、盘点、报损报溢、采购申请、单据详情/列表、库存/流水/报表、库位以及商城后台订单列表/详情/发货/完成均检查仓库范围。仓管销量统计也按授权仓库聚合。演示环境将 `operator` 绑定到首个仓库。
- 验证：静态检查主要 Controller/Service 的仓库 ID 入口及列表过滤；`git diff --check`、后端编译和默认 profile 启动通过；未运行测试。
- 上线注意：既有生产 WAREHOUSE 用户不会自动获得仓库授权，部署后需由管理员在“用户与权限”页逐个分配。未分配账号会按拒绝访问处理。

### 3. 库存键非空与唯一约束

- 状态：已修复
- 修复内容：库存行首次创建前对稳定的 `Item` 行加数据库悲观锁，持锁后重新按物品/仓库/库位/批次查询；并移除商城库存回滚的旁路建行逻辑。这样所有应用内库存创建都会经过同一串行化入口，含 `NULL` 批次的复合唯一键不会再被并发插入绕过。
- 验证：静态搜索确认 `new Inventory(...)` 仅保留在集中库存创建路径；后端编译及默认 profile 启动通过；未运行并发测试。

### 4. 商城预占并发控制

- 状态：已修复
- 修复内容：下单流程先通过 `findFifoForOut` 锁定该物品/仓库的现有物理库存行，再以 `PESSIMISTIC_WRITE` 当前读锁定有效预占行并在 Java 中合计。避免 MySQL `REPEATABLE READ` 下普通 `SUM` 延用下单事务早期读快照。
- 验证：静态确认预占流程不再调用非锁定 `sumHeldQuantity`；后端编译及默认 profile 启动通过；未运行并发测试。

### 5. 仓储出库遵守预占量

- 状态：已修复
- 修复内容：新增 `InventoryReservationGuard`，统一先锁物理库存批次，再锁未过期的预占行。扫码出库、调拨出库、盘点减量、单据反审减量均检查扣减后物理库存不得低于有效预占；商城支付/货到付款扣减仅将本订单预占从保护量中排除，并在完成扣减后消费预占。
- 验证：静态搜索确认普通出库和商城履约均使用该 Guard；`git diff --check`、后端编译和默认 profile 启动通过；未运行并发测试。多商品单据的并发死锁仍由数据库事务回滚保护，后续可按实际冲突指标评估统一的多键排序与重试。

### 6. 盘点期间库存变化检测

- 状态：已修复
- 修复内容：库存实体增加 JPA `@Version`；建盘点单时把版本存入盘点明细；执行盘点通过锁定库存行后比较快照版本，期间任一入库/出库/调拨/调整导致版本变化都会要求重新盘点。迁移前创建的旧盘点行以 `-1` 标记并拒绝执行，避免把缺少版本来源的旧数据当成可信快照。
- 数据库变更：新增 `V7__stocktake_inventory_version.sql`，为库存和盘点行增加版本列。
- 验证：静态检查版本在盘点创建时采集、在库存行锁内比较；V7 已随默认 profile 启动在 H2 上应用；后端编译通过，未运行测试。

### 7. 原库存流水只允许冲销一次

- 状态：已修复
- 修复内容：反审查询增加 `NOT EXISTS`，排除已存在 `reversal_of_transaction_id = 原流水ID` 的流水；新增唯一索引 `uk_tx_reversal_once` 防止并发或异常路径重复冲销。
- 数据库变更：新增 `V8__unique_inventory_transaction_reversal.sql`。
- 验证：静态检查查询谓词和唯一约束定义；V8 已随默认 profile 启动在 H2 上应用；未运行测试。已有数据库如存在重复 `reversal_of_transaction_id`，V8 会拒绝建索引，部署前需先核对并人工处置重复冲销数据。

### 8. 写接口服务端幂等

- 状态：已修复
- 修复内容：新增 `@Idempotent` 与事务拦截器，按用户、接口和 `Idempotency-Key` 建唯一记录；请求摘要不一致时拒绝，完全相同的重试返回首次响应。幂等记录与业务写操作处于同一数据库事务，失败会一起回滚。覆盖扫码、单据/调拨/盘点/调整/采购创建与流转、商城下单及履约确认等写路径。Web 和两个小程序对相同未决请求复用本地 key，成功后清除。
- 数据库变更：新增 `V9__idempotent_request_records.sql`。
- 验证：静态确认注解覆盖的接口及三个前端客户端均生成/发送 `Idempotency-Key`；V9 已随默认 profile 启动在 H2 上应用；后端编译通过，未运行重放/并发测试。
- 接口兼容：被 `@Idempotent` 标记的接口现在要求 `Idempotency-Key`，第三方调用方需补传该请求头。

### 9. 单据列表分页与两阶段读取

- 状态：已修复
- 修复内容：入出库、调拨、盘点、报损报溢和采购申请列表先按创建时间分页查询主键，再对当前页 ID 执行 fetch join 获取关联明细；仓管列表查询同时按授权仓库过滤。API 统一返回 `{records,total,page,pageSize}`，Web 表格改为服务端分页，小程序单据列表按页加载。
- 验证：静态检查列表 Service 已不再调用全量 `findAllDetailed()`；Web 与两个小程序构建通过；后端编译通过，未运行测试。
